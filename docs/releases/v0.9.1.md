## v0.9.1 — 18/20 不该长得像 20/20

**如果你只用 `subs` 抓过一两次、每次都十几条，这一版对你没什么用。** 靠 `serve` 面板排队的、一次几十条上百条的，这一版是给你修的。

问题不在抓不抓得到，在**抓完之后你看不出发生了什么**。

### 一个任务跑完，你只知道它「完成了」

老逻辑只有一句：全是错误才判失败。于是这三种结果在面板上是同一个绿点：

```
20 条全取到                   → done
20 条里成了 18 条，2 条挂了    → done     ← 你看不出来
20 条全都没字幕，一个字没取到  → done     ← 产出是零，也是 done
```

第三种最荒唐：`failed` 计数是 0，所以判成功——可你手上什么都没有。

补那 2 条只能整个任务重来。重来意味着把已经成功的 18 条再抓一遍，再吃一次风控，运气不好那 2 条照样挂，还可能连累其他条。

### 现在结果里带一个词，说清这轮到底什么样

```json
{ "outcome": "partial", "ok": 18, "no_subtitle": 0, "failed": 2 }
```

四个值，判定看的是**产出**，不是「有没有报错」：

- `complete` — 每条都取到
- `partial` — 有产出，但差了几条（失败或没字幕）
- `empty` — 零产出：全都没字幕，或者指定条目里没有一条真跑得起来
- `failed` — 零产出，且全是错误

分界线是这句：**失败的定义是「全是错误」，不是「有错误」。** 所以「零产出但同时也报了错」判 `failed`，「零产出、全是没字幕」判 `empty`——这两种要分清楚，因为该做的事完全不同：一个是去查风控和登录态，一个是换视频。

### 差的那几条，具体差在哪

以前分 P 级的失败只往 `errors` 里塞一句话，你看到的是「2 条失败」，不知道是哪 2 条、哪个 P。现在有明细：

```json
{ "bvid": "BV1xx", "page": 3, "error": "风控校验失败", "retry": "BV1xx#3" }
```

`retry` 字段就是重跑时该写的那个串，直接复制。**单 P 视频不带 `#1`**——写 `BV1abc#1` 虽然也能跑，但看着像「这只是多 P 里的一集」，容易让人以为漏了别的。

面板上是一个 `<details>` 折叠块，点开逐条看，下面一个「只重跑这 2 条」按钮。

### 只补失败的那几条，其余不动

按钮打的是 `POST /api/tasks/{id}/retry-failed`，它**新建一个任务**，只带失败条目。

没有让原任务回队列，是因为原任务的 `result` 是「当时到底发生了什么」的记录——回队列会被这一轮的结果覆盖掉，出问题时你没法回看第一次是怎么挂的。新任务带 `retry_of` 指回原任务，面板上显示「只重跑失败条目 2 条（原任务 T…）」，两条并排在那里。

命令行是同一个能力：

```bash
asr-polish subs --only BV1xx BV1yy#3
```

跑完会打印一行可直接复制的重跑命令。

### `--only` 为什么不走原来的解析流程

这点值得单说，因为它是个很容易踩的坑。

`subs --up 329954990 --limit 20` 失败 2 条之后，如果照常解析 target，拿回来的是「**现在**最新的 20 条」——刚才那 2 条可能已经被新投稿挤出窗口了，你重跑的是一批别的视频。所以 `only` 存在时**直接按 BV 号跑，完全绕开分辨率**，`--limit` 也不参与截断。

### 顺带：`JobFailure` 现在带着明细一起落库

全失败的时候，以前只留一句错误信息，已经跑出来的那 18 条明细全丢了。现在 `JobFailure` 把明细一起带出来写进 result，面板上仍然能看到是哪几条挂了——失败的任务也有话可说。

`fail()` 只在最终 `FAILED` 那支写 result。中途回到 `PENDING`（等待重试）的那支不写，否则你会在一个排队中的任务上看到上一轮的陈旧结果，误判成「已经跑完了」。

### 这一版还没做的

- **顶部统计卡片还是三格。** 想做第四个「部分成功」，得从 JSON 里提 `outcome`，我不确定目标环境里的 SQLite 有没有编进 JSON1 扩展，没敢直接写 SQL。现在四态在任务行和结果框里看得到，汇总仍要自己数。
- **CLI 部分成功仍 exit 0。** 只有全失败才 exit 2。脚本里「有产出就继续」是更常见的需求，改成 exit 3 会让现有管道误判成崩溃。要区分得自己在输出里看 `outcome`。

### 测试

217 → 239 项。新增覆盖：`--only` 的解析与去重、确实绕过 target 解析、按分 P 限定、不被原 `--limit` 截断、四态判定的每个边界（含零产出时同时报错）、分 P 失败带序号、单 P 不带 `#1`、全失败仍携带明细、失败明细落库、回队列路径不写陈旧 result、`retry-failed` 新建任务且不动原任务、无失败时返回 409、CLI `--only` 既不列投稿也只跑指定分 P。
