## v0.7.0 — 服务化：抓取不再被网关超时掐死

批量抓 100 条投稿要几分钟。同步接口扛不住三件事：网关 30 秒就断、页面一关任务跟着废、
1000 个请求同时进来直接过载。这一版把抓取包装成任务队列——请求只登记，执行交给 worker，
状态落在 SQLite。**仍然零依赖**（`sqlite3` + `http.server`，不引 Celery、不装 Redis）。

### 新增

- **`asr_polish/server/`**：一个最小但完整可用的任务队列
  - `store.py`：SQLite 任务表 + 严格状态机。非法迁移抛 `StateError`，终态（`done`/`failed`）
    不允许重复设置；`claim()` 用 `BEGIN IMMEDIATE` 先拿写锁再 `SELECT`+`UPDATE`，
    两个 worker 不可能领到同一行（CAS）；`reclaim_stale()` 回收心跳超时的僵尸任务。
  - `worker.py`：worker 池、进度心跳、janitor 线程（定时扫僵尸）。
  - `jobs.py`：任务执行器。`target` 支持四种写法：`BV号` / `up:mid` /
    `season:mid:sid` / `search:关键词`。
  - `app.py`：REST 接口 + 每 3 秒刷新的只读面板。
- **CLI 三个新命令**：`serve`、`submit --wait`、`status`。
- **测试 89 → 115**：新增状态机非法迁移、并发抢任务、重试、僵尸回收、HTTP 路由。

### HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/` | 任务面板（只读，3 秒自动刷新） |
| `GET` | `/api/health` | 存活 + worker 状态 + 各状态计数 |
| `POST` | `/api/tasks` | 提交任务，`202` 返回任务对象（含 `id`） |
| `GET` | `/api/tasks?status=&limit=` | 列任务 |
| `GET` | `/api/tasks/{id}` | 单个任务的进度、结果、错误 |
| `POST` | `/api/tasks/{id}/retry` | 把 `failed` / `running` 放回队列，`202`；`done` 返回 `409` |

### 修复

- **`pyproject` 的 `packages` 写死成 `["asr_polish"]`** —— 新增的 `server` 子包不会进 wheel，
  `pip install` 后 `asr-polish serve` 直接 `ImportError`。改为 `packages.find`。
  这个 bug 只有「装完之后」才会暴露，本地跑源码永远看不见。

### 四个坑（代码里都留了注释）

1. **每次连接都执行 `PRAGMA journal_mode=WAL`** —— 并发下写事务变成 `readonly database`。
   WAL 是持久化在库文件里的属性，初始化时设一次就够。
2. **每次操作都 open/close 连接** —— 高频并发下同样撞 `readonly`，顺便还慢。
   改成线程本地复用一条连接。
3. **`with sqlite3.connect(...) as conn` 只提交事务、不关闭连接** —— 长连接会泄漏。
4. **`_check_transition` 里 `src == dst` 直接放行** —— 导致「重复 finish」被当成无操作，
   这会让「同一个任务被完成两次」这类 bug 永远查不出来。终态现在必须报错。

### 变更

- `serve` 的默认参数：`127.0.0.1:8040`、2 个 worker、僵尸判定 600 秒。
- `submit` 默认只提交不等（异步语义）；加 `--wait` 才阻塞到结束并打印进度。

### 安装

```bash
pip install git+https://github.com/angus-hu-gzy/asr-polish.git@v0.7.0
```

### 用法

```bash
# 起服务（含 2 个 worker），浏览器打开 http://127.0.0.1:8040 就是面板
asr-polish serve --port 8040

# 提交一个批量任务，立刻返回任务 id
asr-polish submit up:329954990 --limit 50 -o ./subs

# 阻塞到跑完，边跑边看进度
asr-polish submit up:329954990 --limit 50 --wait

# 查队列 / 查单个任务 / 只看失败的
asr-polish status
asr-polish status T6b9722e067
asr-polish status --state failed
```

也可以直接打接口：

```bash
curl -X POST http://127.0.0.1:8040/api/tasks \
  -H "Content-Type: application/json" \
  -d '{"kind":"subs","target":"BV1Mshg6REo4","formats":["txt","srt"],"outdir":"./subs"}'
```

### 实测

3 个任务同时提交，2 个 worker：

| 任务 | 耗时 | 结果 |
|---|---|---|
| 单视频 273s | 1.06s | `done` |
| 单视频 | 1.05s | `done` |
| UP 主 2 条 | 2.39s | 1 条有字幕、1 条无字幕正确跳过 |

前两个并行处理，第三个在队列里等；提交瞬间就返回，不等结果。

### 边界说明

**这是单机队列，不是分布式队列。** 单机、单库、无鉴权，默认只监听 `127.0.0.1`，
对外必须先套反向代理做鉴权与限流。多机部署得换 PostgreSQL 或 Redis。

写它是为了把「请求 / 任务 / 状态 / 重试」这套骨架摆清楚，**不是替代 Celery**。
真实生产环境里，`worker` 进程数、幂等键、死信队列、可观测性都还需要单独设计。
