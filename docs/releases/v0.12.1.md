## 两个自己撞出来的坑

```bash
pip install -U asr-polish
```

0.12.0 发出去之后用它跑了一遍真实任务，撞到两个会真出错的地方。都不是新功能写错，
是旧代码在一个没被试过的路径上露了头。补丁版，只修不加。

### ① Windows 上，中文一出现整条命令就崩

跑 `ffmpeg` 用的是 `subprocess.run(..., text=True)`。这个参数看起来只是「把 bytes 变成
str」，实际上它拿**系统区域编码**去解码：中文 Windows 是 `cp936`，英文 Windows 是
`cp1252`。而 `ffmpeg` 往 stderr 写的是 **UTF-8**。

只要它输出里带一个中文（视频标题、文件路径、编解码器名都可能带），解码就抛
`UnicodeDecodeError`。异常发生在读线程里，线程当场死掉，`stdout` 跟着变成 `None`，
最后由调用方收到一句「转写失败」——**没有任何能看的原因**。日志里翻不到错在哪，
因为它看起来像转写本身失败了。

现在子进程的输出一律自己解码：先按 UTF-8 严格解，失败退回区域编码并替换坏字节，
任何情况下都返回一段能看的字符串。超时也给一句人话：`ffmpeg` 10 分钟没跑完，说的是
「视频可能太长或网络不通」，而不是 `TimeoutExpired`。

这条路 Windows 用户必撞，区别只是字幕里有没有中文。

### ② 切了分 P，搜索还按整篇算

搜索是在整个页面上找节点，不是只在当前篇里找。切到第二篇之后，第一、二篇里同词的
句子仍然被算进命中数。于是会出现这种事：角标写着「12 处」，在当前篇里点「下一处」，
点到第 3 下就没反应了——剩下 9 处都在别的篇里，看不见也点不到。

现在只收当前篇里可见的命中，切篇时把别的篇的高亮一并擦掉，数字跟着这一篇走。

### 测试

357 项（+11）。

新增 `tests/test_bili_output.py` 专测输出解码：UTF-8 中文、`cp1252` 的弯引号、`cp936`
的 GBK 字节、混着坏字节的流，四种输入都得解出一段能看的字符串而不是抛异常。
这类 bug 靠「跑一遍看看」是抓不住的——得在测试里手动造出那几种字节。

CI 里 node 子进程的输出也改成显式 UTF-8 解码。Windows runner 上它原来是红的，
而红的原因和 ① 是同一个：拿区域编码去解 UTF-8。

### 没变的

- 抓取、限速、风控退避、任务状态机，一行没动。
- 阅读页的四个功能、`transcript` 接口结构、页面无框架无构建的形态，都没动。
- 仍然只监听 `127.0.0.1`，没有鉴权，不做账号。
