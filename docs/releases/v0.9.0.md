## v0.9.0 — 一个任务不会再被跑两遍

**只用 `subs` 命令行抓字幕的话，这一版对你几乎是空转。** 只要你用过 `serve` 的面板、点过「重试」，就该升。

这一版修的是一个能把任务状态写坏的问题：**同一个任务，被两份执行同时跑。**

### 问题是怎么发生的

面板上的「重试」按钮，对**正在跑**的任务也放行。点了之后状态回到排队，另一个 worker 领走开始跑——可原来那份还在跑，没有人通知它停。

两份执行抢着写同一行状态、同一个字幕文件。实测的时序是这样的：

```
worker-A 领走任务
你点「重试」        → 状态回到 pending
worker-B 领走任务    → 同一个任务，两份执行同时存在
A 刷心跳            → 进度写着 0.30，可这是 B 的进度被 A 覆写了
A 先跑完 finish     → 任务被标成「完成」，而 B 还在跑
B 跑完 finish       → 抛 StateError，日志打出「失败，已重新排队」——其实什么都没排
```

表面上任务是「完成」了，可你拿到的那份字幕可能是半截的：A 写到一半，B 正在把同一个文件截断重写。日志还在说谎。

### 还有第二个入口，一个人都没点过重试

worker 因为垃圾回收停顿、笔记本合盖休眠，心跳断了几分钟。回收器认定它是僵尸任务，放回队列，新 worker 领走。旧的 worker 醒来后接着跑，跑完写回「完成」——而「进行中 → 完成」本来就是合法迁移，状态机拦不住。

于是一个**还在跑**的任务被提前标成完成，真正在跑的那份结果没有任何人被通知。

### 怎么修的：给每次执行发一张房卡

任务表加了一列 `attempt`，每次被领走就加一。worker 记住自己领到的是第几轮，之后每一次写状态（心跳、成功、失败）都带上「我是第 3 轮」。

数据库那条 `UPDATE` 于是变成 `WHERE id=? AND attempt=?`。如果这行已经被别人领到第 4 轮，条件不匹配，写不进去。

关键在于**这是写的时候顺手判断，不是先查再写**——先查后判中间有个窗口，正好够另一份执行插进来。

于是三件事变成确定的：

- **心跳写不进去 → 立刻停手。** 旧 worker 在下一次心跳（1 秒内）就知道自己出局了。
- **`finish` 被拒 → 结果直接丢弃。** 日志写「任务已被接管」，不再是那句假的「已重新排队」。
- **`fail` 被拒 → 这次的失败不记在别人头上。** 以前旧执行撞上终态会转去调 `fail`，而 `fail` 见终态直接返回，什么都记不下，还顺带把新执行的错误信息盖掉。

僵尸回收那条路径也一起改了：两条 `UPDATE` 都带 `attempt = attempt + 1`，旧令牌当场作废。

### 顺带：字幕文件改成原子写

`write_all` 原来是 `path.write_text`——先截断再写。两份执行写同一个文件名时，读的人会看到被截断的文件。现在改成同目录临时文件 + `os.replace`：读者要么看到旧的完整版，要么看到新的完整版，没有中间态。

### 顺带：同一份 Cookie 导入第二次不会再写盘

`asr-polish cookie set` 每次都会把结果写回文件，即使内容一个字都没变。这个空转在 Linux 上无成本，在 Windows 上会出事——写临时文件、`os.replace` 替换的那一刻，杀软正在扫这个刚生成的文件，于是报「拒绝访问」。

这是打标签那天 CI 自己撞出来的：同一个提交，主分支那轮全绿，标签那轮红了两个 job，报错就是这句 `WinError 5`。

两处改了：内容没变就整个跳过写盘；真撞上占用，按 0.05 / 0.1 / 0.2 / 0.4 秒重试四次，仍然失败才报「文件被别的程序占着（杀软正在扫描、或编辑器正开着它）」——原文件不动，临时文件清理干净，不会留下半份 Cookie。

同一套重试也给了字幕导出：`write_all` 的原子写撞的是同一种锁，之前一样没有退路。

### 顺带：Python 3.9 上不会再假装「没登录」

打标签那天的 CI 里，ubuntu + Python 3.9 挂了一条，报的是「写入的内容里没解析出任何 cookie」。可那份 Cookie 完全合法——是本项目的测试数据，同一份在 3.10 / 3.11 / 3.12 / 3.13 上都过了。

差在 `#HttpOnly_` 这个前缀。浏览器插件导出的 cookies.txt 里，SESSDATA 几乎总是写成：

```
#HttpOnly_.bilibili.com	TRUE	/	TRUE	1999999999	SESSDATA	xxxxx
```

而 Python 3.9 的 `http.cookiejar` 会把所有 `#` 开头的行当注释整行丢掉，3.10 起才剥掉前缀当正常行处理。于是同一个文件，3.10+ 能登进去，**3.9 读到 0 条**。这不只是测试红：`cookie` 检查会显示「格式不对」，导入会直接被拒，而更隐蔽的是发请求时那个 jar 是空的——等于一直在未登录状态下跑，然后对着「风控校验失败」猜原因。

现在改成自己解析 Netscape 行，不再依赖标准库的版本行为。顺带宽了一点：一条坏行只跳过它自己，不再让整份文件失败——真实导出文件里混进半行太常见了，让用户手工改不现实。

### 顺带：Windows 上 `asr-polish subs --help` 不该崩

同一轮 CI 里 Windows 那个红得更莫名其妙：`subs --help`，0 秒，`UnicodeEncodeError: 'charmap' codec can't encode characters`，紧接着的测试步骤直接被跳过。

原因是 stdout 重定向到管道时用的是系统代码页，西文机器是 cp1252，打不出帮助里的中文。真实用户在 `asr-polish subs --help > help.txt`、或者在 CI 里跑同一件事，撞的是同一个坑。

入口现在会先把输出流调成 UTF-8（非终端时）并降级成 `errors="replace"`；真正的控制台不动编码——Windows 控制台本来走 `WriteConsoleW`，硬改反而会在老 conhost 里变乱码。

### 这一版还没做的

worker 要等到下一次心跳（1 秒内）才发现自己出局，`jobs.run` 正在跑的那一批——比如正在下的音频——不会立刻中断，会跑完再把结果丢掉。

要立刻停手，得给 `jobs.run` 传一个中断回调，让它每处理完一条就检查一次。这一版没做。影响的是**浪费几秒**，不是正确性：结果已经写不进去了。

### 变更

- `retry` 对「进行中」的任务，语义明确为**强制重启**，响应体多了 `note` 字段说明「原执行的结果会被丢弃」。对「失败」任务的重试行为不变。
- 任务 JSON 多了 `attempt` 字段，能直接看出这个任务被重启过几次。
- `Store.finish()` / `heartbeat()` 返回 `bool`（是否写入成功），`Store.fail()` 返回 `Optional[str]`（`None` = 令牌已过期，这次失败不该由我记录）。三者都新增可选参数 `attempt`，不传就不校验，管理员路径与旧调用不受影响。

### 升级

已有的 `tasks.db` 在打开时会自动 `ALTER TABLE` 补上 `attempt` 列（默认 0），**不需要删库重建**，也不影响队列里的历史任务。

### 测试

192 → 217 项。新增覆盖：令牌单调递增、`running` 重试后旧执行的三类写回全被拒、僵尸回收后旧执行不能抢先标完成、重试预算用尽的回收也照样作废旧令牌、旧库自动迁移且幂等、worker 被接管后丢弃结果而不是记失败、原子写不留临时文件、Cookie 内容未变不重写、替换撞锁重试、持续占用时保留原文件并清理临时文件、带 `#HttpOnly_` 的 SESSDATA 能读回且合并时保留标记、一条坏行不影响整份文件、cp1252 管道下 `--help` / `--version` / 无命令三条路径都不崩。

### 安装

```bash
pip install git+https://github.com/angus-hu-gzy/asr-polish.git@v0.9.0
```

从 0.8.x 升级不用改任何调用方式，没有新增命令和参数。
